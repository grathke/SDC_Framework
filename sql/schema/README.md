# Full schema build

A from-scratch build of the database the application expects. `sql/` beside this folder holds 160
incremental migrations, which assume a database that already exists — these four files are the
thing they were always missing.

Generated by `scripts\dump-schema.ps1`, read straight from the system catalogs of the live
database. **Do not edit them by hand.** Regenerate instead, or the next run silently discards the
correction:

```
powershell -ExecutionPolicy Bypass -File .\scripts\dump-schema.ps1
```

## Not yet proven

Every file here parses against SQL Server 2025, which catches syntax and nothing else. **No
database has ever been built from them.** Doing that needs a scratch database to run them into and
an object-by-object comparison against `WX_Framework`; until someone does it, treat a clean run as
the first real test rather than a formality.

## Run order

The numbers are the order, and it matters:

| File | What it creates |
|---|---|
| `01_tables.sql` | 40 tables with their columns, identities, computed columns, primary keys, unique and check constraints, and all 100 defaults |
| `02_foreign_keys.sql` | 24 foreign keys, applied after every table exists |
| `03_indexes.sql` | 34 non-constraint indexes |
| `04_programmability.sql` | 5 views, 4 stored procedures, 1 function |
| `10_reference_data.sql` | Static lookups — genders, date and time formats, time zones, registration types, licence terms, issue categories, role templates |
| `11_registration_and_admin.sql` | One registration and one administrator account |
| `12_framework_definition.sql` | Pages, roles, the role schema, and the 538 field permissions that decide what anyone sees |
| `13_zip_codes.sql` | 80,305 US zip codes. **Optional** — 22 MB, and the application starts without it |

Files `10` upward are generated by `scripts\dump-seed.ps1`, the same way and with the same rule
about not editing them by hand. The order is not cosmetic: `FW_Registration` has foreign keys into
four of the lookup tables, `FW_Roles` has one into `FW_Registration`, and `FW_RoleDetails` has one
into `FW_RoleSchema`.

## Signing in the first time

`11_registration_and_admin.sql` creates one account — user name **`admin`**, password
**`ChangeMe1`** — and nothing else can log in. **Change that password immediately.** It is written
in a file in this repository, so it is public to everyone who can read the repository.

The stored hash is HMAC-SHA512 over the password keyed on the user's own `UserId`, which is why
the bootstrap account has a fixed id of 1: the hash cannot be computed without knowing it.

One trap, recorded because it cost time and would have shipped an account nobody could use. The
hash bytes are read back as a UTF-16 string, and an HMAC routinely produces 16-bit units in the
surrogate range with no pair to match. .NET replaces each of those with U+FFFD when it builds the
string; SQL Server keeps them exactly as given. The seed therefore stores the *post-replacement*
bytes — what VB.NET actually holds — not the raw HMAC. Writing the raw hash produces a row that
looks correct in every way and rejects the password every time.

Each statement in `01_tables.sql` is guarded by `IF OBJECT_ID(...) IS NULL`, so running it against
a database that already has some of the tables adds the missing ones rather than failing. The other
three files are not guarded and expect to run once, against an empty database.

`04_programmability.sql` is ordered by dependency rather than by type or name. Neither `CREATE VIEW`
nor `CREATE FUNCTION` tolerates a forward reference — only stored procedures get deferred name
resolution — and three objects here reference each other: `fn_GenerateRandomCode` reads
`vw_RandomGuid`, `FW_UserPeople` reads `vw_FW_CurrentUser`, and `usp_FW_RefreshSwitchUser` reads
`FW_UserPeople`. Sorting by name puts each of those the wrong way round.

## What is deliberately not here

**Credentials.** `FW_Users` holds 10,014 rows, 15 of them with a password hash, 15 with a value in
the legacy plaintext `Password` column, and 3 with a TOTP key. None of it travels. Neither do the
`Smarty_AuthID`, `Smarty_AuthToken` and `Smarty_EmbeddedKey` address-validation keys on
`FW_Registration` — those are live third-party credentials, excluded by name in the generator.

**Other people's data.** Registration 2, SARALAND, is a real client and does not seed. Only
registration 1, DEVELOPMENT TEAM, does. Employees, the audit trail, sessions, messages, help desk
issues, login attempts, the error log, saved searches and generated page requests are all left
behind.

**Per-user state.** `FW_PageZooms` and the `FW_TableLayouts` rows belonging to a user stay out. The
user-less `FW_TableLayouts` rows do travel — those are the `QbeDefault` search-field arrangements,
which belong to the page rather than to a person.

**SQL Server logins.** Nothing here creates a login or grants anything. Whoever builds the database
grants access themselves, and no database password is ever written into this repository.
